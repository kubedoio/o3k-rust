# O3K v0.2.0-alpha.1 known limitations

This document records the known limitations of the v0.2.0-alpha.1 release
candidate. It is candidate-scoped: `docs/release-tracker.md` stays the
authoritative release gate with `program_status: blocked` and
`closure_decision: pending`, the release gate (issue #93) remains blocked on
the independent human architecture/security review (issue #92), and issue #94
owns the closure chain. This document is therefore not a claim that the
release has shipped; create a tag only after `packaging/release-gate.sh`
reports `status: ready` with `--source-commit` and `--human-review`.

## native-rust-testlab

- alpha/TestLab scope only: the first native ephemeral-root alpha
  (SPEC-0025 step 8), not a production service.
- single-controller posture only; no HA / multi-controller behavior
  (`docs/status/current-state.yaml` lists HA/multi-controller behavior under
  `explicitly_unproven_claims`).
- SQLite only: SQLite is the supported default for the minimal TestLab and
  portable profiles. PostgreSQL is planned but NOT supported (no real adapter
  and conformance suite exist yet).
- libvirt/KVM profile only; shipping is `o3k-compute` + libvirt — no CellHV
  shipping in this release.
- config-drive instead of an HTTP metadata service (`metadata-API` is an
  unsupported Nova operation).
- intentionally bounded Nova/Neutron/Glance/Keystone compatibility: see the
  `unsupported_operations` lists in `compatibility/openstack-targets.yaml` —
  no security groups, floating IPs, routers, metadata API, live migration,
  rescue, rebuild, boot-from-volume, import, snapshots, or backup.
- no native persistent-volume / boot-from-volume service.
- ~50 MB is an unmeasured target, not a guarantee
  (`docs/status/current-state.yaml` lists the 50 MB footprint under
  `explicitly_unproven_claims`).
- historical machine evidence is source-bound to ancestor commits and is stale
  after the rejected-candidate remediation.  A fresh candidate-bound
  recertification, including real-host lifecycle, failure/recovery, clean
  installs, and benchmark evidence, is still required; issue #92 remains open.

## openstack-service-testbed

- volumev3 is external-hosted only (SPEC-0023): O3K supplies the surrounding
  identity, Glance, Nova attachment, and CHAP-secure compute surface while
  Cinder retains its own database, message bus, service processes, and
  backend. `docs/status/current-state.yaml` lists O3K-implemented Cinder under
  `explicitly_unproven_claims`.
- external-Cinder/Tempest success does not imply native Cinder support or
  native alpha readiness (`docs/status/current-state.yaml`: "external-Cinder/
  Tempest success ... does not satisfy the native alpha gate").
- run-bound evidence is not current-commit evidence: the protected real-Cinder
  evidence is run-bound and "must never be presented as current-commit
  evidence" (`docs/status/current-state.yaml`, `evidence_bound`).

## small-edge-cloud

- not released: no release claim is made for this profile
  (`docs/status/current-state.yaml`, `release_relevance`: "No release claim").
- no production / HA / multi-host / multi-controller evidence: no multi-host
  implementation, inventory, scheduling, fencing, database, or evidence work
  exists.
- production-readiness unproven (`explicitly_unproven_claims`).

## Follow-ups and review disposition

These items must not be promoted to a release approval without the stated
disposition:

- #575: remediation now uses a deterministic fresh delete command identity
  after presence observation, with strict acceptance of the original or
  redrive operation and a portable regression test.  A libvirtd-restart
  mid-define real-host convergence run remains required before this limitation
  can be removed from the candidate gate.
- C6: fresh run `987654343` reproduced a TAP-ownership/DHCP rollback failure
  caused by the disposable profile's shared bridge name.  Commit `5c65db9`
  isolates disposable bridges per run, and run `987654344` removed its run
  bridge cleanly.  A complete passing lifecycle on a fresh host is still
  required before this limitation can be removed; `9f412e4` also corrects
  cleanup to inspect the compute-owned network/DHCP ledgers, and `02a294f`
  refuses state discard when the deterministic bridge remains without a
  ledger. The old residual
  bridge remains intentionally untouched because its ownership ledger was
  already discarded. Fresh run `987654403` additionally exposed Linux
  bridge-MAC drift after TAP preparation; the network manager now assigns a
  stable locally-administered bridge MAC before recording ownership. Fresh run
  `987654406` confirmed stable bridge identity and owned cleanup, but the
  CirrOS console boot-marker assertion still failed, so a complete host
  lifecycle after that fix remains required. The limitation remains
  release-blocking for the candidate gate.
- rare duplicate artifact-offer race on create: commit `a713f48` makes a
  retry with the same immutable transfer identity idempotent while still
  rejecting content/command/resource changes. Fresh run `987654346` committed
  both image and config-drive transfers without the prior offer-conflict
  disconnect, although the subsequent host create still failed. A complete
  lifecycle run with no duplicate artifact or leaked allocation is still
  required before this item can be removed from the candidate gate.
- benchmark-observed post-crash delete inconsistency (first delete reported
  absent while the server stayed ACTIVE; second delete cleaned; recorded in
  the benchmark raw `failures_and_notes`) is release-blocking until reproduced
  and fixed or explicitly reclassified by an independent human reviewer. It
  must not be described as a non-blocking limitation.
