# O3K v0.4.0-alpha.1 — release candidate draft

This document is a release-candidate checklist, not a claim that the release
has shipped. The release gate remains blocked until real libvirt E2E, failure
recovery, clean Ubuntu and Debian installation artifacts, measured benchmark
data, upgrade/rollback acceptance artifacts, and an approved human-review
artifact bound to the candidate commit all report the required status.

## What changed since v0.3.0-alpha.1

v0.4.0-alpha.1 is the first upgrade/rollback milestone (#626): the `o3k`
operator CLI gains `o3k version`, `sudo o3k upgrade` (`--to`, `--check`,
`--yes`, `--json`) and `sudo o3k rollback`, with the design recorded in
`docs/plan/o3k-upgrade.md`:

- a durable 12-phase upgrade state machine persisted at
  `/var/lib/o3k/.o3k-upgrade-state.json`; interruption resumes from the
  recorded phase or rolls back, and a per-invocation lock prevents
  concurrent upgrades;
- official GitHub Release assets only: tarball + published `.sha256` +
  `install.sh`, bundle `SHA256SUMS` coverage, manifest version/profile/
  installer digest, and the new `upgrade_from.min_version` fence — no
  unverified downloads, no executed downloaded scripts, no silent
  downgrades;
- read-only preflight (distro/arch, disk space, ownership manifest, binary
  hashes, SQLite integrity + schema version, doctor release-category gate);
- an ownership-safe backup under `/var/lib/o3k/backups/` (private 0700/0600)
  with a crash-consistent `VACUUM INTO` SQLite snapshot, verbatim config/TLS
  copy, release metadata, the old binary set, and the recorded
  migration-compatibility decision (`db_restore_required_on_rollback`);
  migrations stay owned by o3kd's embedded migrator — the upgrade verifies
  the observed schema version against the release manifest's
  `schema_version` and fails closed;
- compute-stop → control-stop → atomic binary-set replacement →
  control-start → compute-start ordering; existing guests are never
  recreated and libvirt is never restarted; doctor plus public API smoke
  gate the commit;
- rollback restores the immediately previous O3K-created verified backup
  (binaries + manifest + DB only when required) and records the rollback; a
  second rollback is a no-op notice; automatic post-mutation failure
  rollback runs exactly once per invocation, then a recoverable
  `FAILED_UPGRADE` state with instructions;
- three new read-only doctor checks (`release.binary_set_consistent`,
  `release.backup_available`, `release.upgrade_state`) — 31 → 34 checks;
- the installer version fence: fresh install unchanged, same version
  idempotent, newer installed refused, older installed downloads + verifies
  the new release and prints the exact `o3k upgrade` command (curl|sh never
  auto-upgrades an existing installation);
- release manifests now declare `schema_version` and
  `upgrade_from.min_version` (`packaging/make-release.sh`, operator-supplied
  at release time).

## Planned contents

- x86_64 `o3kd`, `o3k`, and `o3k-compute` artifacts built on the Debian 12
  (bookworm, glibc 2.36) release baseline so the same binaries execute on both
  advertised targets (Ubuntu 24.04 and Debian 12); the glibc floor is enforced
  by `packaging/check-glibc-baseline.sh` in `make-release.sh` and
  `verify-release-bundle.sh`;
- release assets: `install.sh`,
  `o3k-0.4.0-alpha.1-linux-x86_64.tar.gz`,
  `o3k-0.4.0-alpha.1-linux-x86_64.tar.gz.sha256`, `o3kd`, `o3k`,
  `o3k-compute`, `SHA256SUMS`, `sbom.spdx.json`, `manifest.json`;
- real-release upgrade/rollback acceptance on Ubuntu 24.04 and Debian 12
  (v0.3.0-alpha.1 → v0.4.0-alpha.1 with REAL published artifacts, same
  resources preserved, reboot recovery, rollback, re-upgrade, zero residue,
  foreign state unchanged) plus the full negative/interruption matrix;
- profile-aware installer, diagnostics, reset, purge, and uninstall commands;
- SBOM, dependency/license policy result, checksums, and provenance manifest;
- OpenStack CLI/clouds.yaml example and CirrOS walkthrough;
- compatibility matrix, security model, architecture, upgrade/rollback
  boundaries, and known alpha limitations.

No production, HA, full-OpenStack, security-group, Cinder, or CellHV-readiness
claim is made. Create a tag only after `packaging/release-gate.sh` reports
`status: ready` with `--source-commit` and `--human-review`; the gate does not
generate approval or substitute for the reviewer's judgment.
